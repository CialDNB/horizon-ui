# 07 — Hosted MCP Server

## Intent

AI agents (Claude Code, Cursor, internal tools) building UI against horizon-ui must get accurate component props, tokens, examples and rules instead of guessing. Unlike x-core's MCP (a stdio server bundled in the npm package, run locally), this server is **deployed as a hosted service on every release** and reachable by any authenticated connection, so consumers install nothing and always see the latest published version.

## Goals

1. Deployed automatically on each release; data always matches the published package version.
2. Remote transport (Streamable HTTP), usable from any MCP client with a URL, no local install.
3. Authenticated: only authorized D&B/CIAL users or services can connect.
4. Read-only. No write tools, no user data.

## Non-goals

- No stdio/npm-bundled variant in v1 (can be added later from the same code).
- No per-user state, no analytics beyond access logs.
- Not a public/anonymous endpoint.

## What it serves

Same six tools as x-core's MCP, generated at build time from the source of truth:

`list_components`, `get_component_info` (props from TS types via react-docgen-typescript), `get_component_example` (from stories), `search_components`, `get_theme_tokens` (from `src/tokens`), `get_constitution_section`.

New in horizon-ui: `get_migration_mapping` (x-core component -> horizon-ui equivalent + API differences, from `docs/migration/component-map.md`) so agents can migrate customer360 screens. Optional `list_versions` / version pinning: the server may hold manifests for the last N versions and accept a `version` argument (builder's call).

The manifest is generated by `scripts/build-mcp-manifest` in the same build that produces `dist/`, then baked into the container image. Server reads only the manifest: no network calls at runtime.

## Where and how it deploys (proposal, grounded in existing infra)

Existing precedent: `x-core-deployment` (helmfile + GitHub Actions) already deploys an `xCoreMcp` release (chart `cial/kubedeploy`, ECR image `cial/x-core-mcp`, port 3939, ingress `<release>.<env>.cial.tech`) to the `dev-old` and `hdev` environments, on EKS with ARC runners. horizon-ui should reuse this path rather than invent a new one.

Proposed flow:

```
release tag on horizon-ui repo
  -> GH Action: build package + manifest, publish npm to GitHub Packages
  -> build MCP image (node:22-alpine, server + manifest), push to ECR cial/horizon-ui-mcp:<version>
  -> PR/commit to horizon-ui-deployment (new repo, decided): add release `horizonUiMcp`, bump image tag
  -> helmfile deploy -> https://horizon-ui-mcp.<env>.cial.tech/mcp
```

- Separate image and release from Storybook (x-core ships Storybook as an nginx image; horizon-ui does the same for Storybook, and the MCP as a second image).
- Tag bump automation: follow the existing pattern (x-core bumps its version in the deployment repo via PR, see commits "bump x-core version to v2.2.24").
- Environments: start with `hdev`; promote to staging/production per the deployment repo's environment model.
- Resources: tiny (x-core-mcp uses 100m CPU / 128Mi request). One or two replicas.

## Authentication (decided: bearer tokens; see 06)

"Any auth connection" means connections must authenticate; the mechanism is open. Options, in order of my preference:

| Option | How | Trade-off |
|---|---|---|
| A. OAuth 2.1 via company IdP | Server acts as OAuth resource server per the MCP authorization spec; clients (Claude Code, Cursor) do the browser login | Best UX and per-user identity; needs IdP details and a bit more code |
| B. Ingress-level auth | Existing ingress/oauth2-proxy / SSO in front; server trusts it | Least server code; browser SSO flow may not work for CLI MCP clients without extra setup |
| C. Static bearer tokens / API keys | Issued per team, stored as k8s secrets, sent as `Authorization` header | Simplest; no identity, manual rotation |

**Decision: option C, bearer tokens.** Per-team tokens stored as k8s secrets, sent in the `Authorization` header; `/healthz` is the only unauthenticated route. Auth lives in one middleware so moving to OAuth (A) later does not touch the tools. Issuing, rotation and revocation process still to be defined (see 06 follow-ups).

Consumer wiring: `.mcp.json` entry of type `http` with the URL (and header for option C). Documented in README of horizon-ui and published in the consumer-facing docs.

## Reuse of x-core MCP code

Port `scripts/mcp-manifest-lib.js` (docgen-based; the x-core notes say a hand-rolled TS AST walk failed on real components, so do not replace it) and the tool handlers. Swap `StdioServerTransport` for the SDK's Streamable HTTP transport plus a `/healthz` endpoint for k8s probes.

## Risks

- Manifest drift vs published package: mitigated by generating both in the same CI job and tagging the image with the package version.
- Auth misconfiguration exposing internal component rules: low sensitivity, but still gated.
- Release pipeline needs permission to open a tag-bump PR in `horizon-ui-deployment`.
